## Introduction

This lab guide covers the **Provisioning and Configuration** section of the **Building Cloud-native Apps with Red Hat OpenShift on IBM Cloud Level 4** course. ## About This Lab

The Summit Insurance scenario is a mid-sized insurance company modernizing its underwriting process using AI-assisted automation. Their application:

- Accepts insurance applications through a web interface
- Processes underwriting decisions asynchronously using Apache Kafka
- Integrates with AI services for driver's license image analysis and underwriting rule evaluation
- Stores data across three different database technologies matched to each data pattern
- Requires high availability, security, and observability from day one

Your role is to provision and configure the complete infrastructure that supports this application.

## Lab 3.3 – Provision Foundational Services

### Objective

Provision the five foundational services required before creating any application infrastructure. These services must exist first so that every resource provisioned after this point is monitored, secured, and audited from the moment it is created.

### Why These Services Come First

The Summit Insurance application has specific compliance and operational requirements:

- Insurance applications must maintain audit trails for all infrastructure changes and access to sensitive data
- Database credentials and API keys must be stored securely — not hardcoded in application code or container images
- Encryption keys must exist before encrypted databases can be provisioned
- The ROKS cluster must have a monitoring and logging destination ready to connect to at cluster creation time

### Services to Provision

| Service | Purpose |
|---------|---------|
| IBM Cloud Monitoring | Cluster and application metrics |
| IBM Cloud Logging | Log aggregation and search |
| IBM Cloud Activity Tracker | Audit trail and compliance |
| IBM Secrets Manager | Secure credential storage |
| IBM Key Protect | Encryption key management |

---

### Step 1 – Create IBM Cloud Monitoring Instance

1. In the IBM Cloud console, click **Catalog** in the top navigation.
2. In the search bar, type `IBM Cloud Monitoring` and select it from the results.
3. On the service creation page, configure the following:
   - **Plan:** Select the Graduated Tier plan
   - **Region:** `us-south`
   - **Resource Group:** Select the resource group from your reservation details
   - **Service name:** `summit-insurance-monitoring`
4. Click **Create**.

<!-- SCREENSHOT: IBM Cloud Monitoring service creation page with fields filled in -->

**Verify:** You are redirected to the service instance page and the status shows **Active**.

> **Why Graduated Tier?** Pay-as-you-go based on data volume. Costs scale with application growth rather than requiring upfront capacity planning.

---

### Step 2 – Create IBM Cloud Logging Instance

1. In the IBM Cloud console, click **Catalog**.
2. Search for `IBM Log Analysis` and select it.
3. Configure the following:
   - **Plan:** Select the 7-day plan
   - **Region:** `us-south`
   - **Resource Group:** Select your assigned resource group
   - **Service name:** `summit-insurance-logging`
4. Click **Create**.

<!-- SCREENSHOT: IBM Log Analysis service creation page with fields filled in -->

**Verify:** The instance status shows **Active**.

> **Why 7-day retention?** Most troubleshooting uses recent logs. Older logs can be archived to Cloud Object Storage for long-term compliance at significantly lower cost.

---

### Step 3 – Configure IBM Cloud Activity Tracker Event Routing

Activity Tracker is no longer a standalone catalog service. It is now configured as **Activity Tracker Event Routing** — a platform-level setting that routes IBM Cloud audit events to a destination of your choice.

1. In the IBM Cloud console, go to **Navigation menu (☰) → Observability → Activity Tracker**.
2. Click **Event Routing** in the left menu.
3. Click **Create target** and configure the following:
   - **Type:** IBM Cloud Logs (recommended — this routes audit events to the same IBM Cloud Logs instance you provisioned in Step 2)
   - **Destination:** Select `summit-insurance-logging`
   - **Target name:** `summit-insurance-activity-target`
4. Click **Create**.
5. Next, click **Create route** to define which events get sent to the target:
   - **Route name:** `summit-insurance-activity-route`
   - **Target:** Select `summit-insurance-activity-target`
6. Click **Create**.

<!-- SCREENSHOT: Activity Tracker Event Routing page showing target creation with IBM Cloud Logs selected -->

<!-- SCREENSHOT: Activity Tracker Event Routing page showing completed route -->

**Verify:** The target and route both appear in the Event Routing list with an active status. IBM Cloud audit events will now flow to your IBM Cloud Logs instance.

---

### Step 4 – Create IBM Secrets Manager Instance

1. In the IBM Cloud console, click **Catalog**.
2. Search for `Secrets Manager` and select it.
3. Configure the following:
   - **Plan:** Standard
   - **Region:** `us-south`
   - **Resource Group:** Select your assigned resource group
   - **Service name:** `summit-insurance-secrets-manager`
4. Click **Create**.

<!-- SCREENSHOT: Secrets Manager service creation page with fields filled in -->

**Verify:** The instance status shows **Active**. Click into the instance and confirm you can navigate to the **Secrets** page.

> **Why Secrets Manager instead of Kubernetes Secrets?** Kubernetes Secrets are base64-encoded, not encrypted at rest by default. Secrets Manager provides true encryption, centralized management, automatic rotation, and a full audit trail — all required for a regulated insurance application.

---

### Step 5 – Create IBM Key Protect Instance

1. In the IBM Cloud console, click **Catalog**.
2. Search for `Key Protect` and select it.
3. Configure the following:
   - **Plan:** Tiered Pricing
   - **Region:** `us-south`
   - **Resource Group:** Select your assigned resource group
   - **Service name:** `summit-insurance-key-protect`
4. Click **Create**.

<!-- SCREENSHOT: Key Protect service creation page with fields filled in -->

---

### Step 6 – Create Root Keys in Key Protect

Root keys are used to encrypt the databases you will provision in Lab 3.5. They must exist before the databases are created.

1. Open the `summit-insurance-key-protect` instance.
2. Navigate to **Keys** in the left menu.
3. Click **Add key**.
4. Select **Create a key** and then **Root key**.
5. Enter the name `summit-database-root-key` and click **Create key**.

<!-- SCREENSHOT: Key Protect Add key panel with root key type selected and name entered -->

6. Repeat steps 3–5 to create a second root key named `summit-storage-root-key`.

**Verify:** Both root keys appear in the Keys list with status **Active**.

> **Why two root keys?** Separate keys for databases and object storage allow independent rotation. If one key is rotated, the other is unaffected.

---

### Step 7 – Create IAM Authorization Policies

Service-to-service IAM authorizations allow IBM Cloud services to communicate with each other securely, without requiring hardcoded credentials.

1. In the IBM Cloud console, go to **Manage → Access (IAM)** in the top navigation.
2. Select **Authorizations** from the left menu.
3. Click **Create**.
4. Configure the first authorization policy:
   - **Source service:** IBM Cloud Databases
   - **Target service:** Key Protect
   - **Target service instance:** `summit-insurance-key-protect`
   - **Role:** Reader
5. Click **Authorize**.

<!-- SCREENSHOT: IAM Authorizations Create page with IBM Cloud Databases → Key Protect policy configured -->

6. Click **Create** again and configure the second policy:
   - **Source service:** Secrets Manager
   - **Source service instance:** `summit-insurance-secrets-manager`
   - **Target service:** Key Protect
   - **Target service instance:** `summit-insurance-key-protect`
   - **Role:** Reader
7. Click **Authorize**.

**Verify:** Both authorization policies appear in the Authorizations list.

> **Note:** The authorization policies connecting the ROKS cluster to Monitoring and Logging are created automatically in Lab 3.4 when you enable observability on the cluster.

## Lab 3.4 – Provision the ROKS Cluster

### Objective

Provision the VPC networking and Red Hat OpenShift on IBM Cloud (ROKS) cluster that will host the Summit Insurance application, then connect the cluster to the foundational observability services.

> **Note:** Cluster provisioning typically takes 15–25 minutes after you submit the creation request.

---

### Step 1 – Create VPC Networking

ROKS requires VPC networking. You will create a VPC with three subnets — one per availability zone — to support multi-zone high availability.

1. In the IBM Cloud console, navigate to the **Navigation menu (☰) → VPC Infrastructure → VPCs**.
2. Click **Create**.
3. Configure the VPC:
   - **Name:** `summit-insurance-vpc`
   - **Region:** `us-south`
   - **Resource Group:** Select your assigned resource group
   - **Default address prefixes:** Leave address prefix creation checked
4. In the **Subnets** section, create three subnets — one for each zone:
   - Subnet 1: Name `summit-insurance-subnet-zone1`, Zone `us-south-1`
   - Subnet 2: Name `summit-insurance-subnet-zone2`, Zone `us-south-2`
   - Subnet 3: Name `summit-insurance-subnet-zone3`, Zone `us-south-3`
5. For each subnet, attach a **Public gateway**. If public gateways do not yet exist for each zone, create them when prompted.
6. Click **Create VPC**.

<!-- SCREENSHOT: VPC creation page showing name, region, and three subnets configured across zones -->

**Verify:** The VPC shows status **Available**. All three subnets are listed, each with a public gateway attached.

> **Why three subnets and public gateways?** Multi-zone subnets ensure the application continues running if one availability zone experiences an outage. Public gateways allow pods to pull container images from registries and make outbound API calls to AI services.

---

### Step 2 – Create the ROKS Cluster

1. In the IBM Cloud console, navigate to **Navigation menu (☰) → Kubernetes → Clusters**.
2. Click **Create cluster**.
3. Select **OpenShift** as the cluster type.
4. Configure the cluster with the following settings:

   | Setting | Value |
   |---------|-------|
   | **Name** | `summit-insurance-cluster` |
   | **Infrastructure** | VPC |
   | **VPC** | `summit-insurance-vpc` |
   | **Resource Group** | Your assigned resource group |
   | **OpenShift version** | Select the latest available stable version |
   | **Worker node flavor** | `bx2.4x16` (4 vCPU, 16 GB RAM) |
   | **Worker nodes per zone** | 1 |

5. Under **Worker zones**, select all three zones and assign the corresponding subnets:
   - `us-south-1` → `summit-insurance-subnet-zone1`
   - `us-south-2` → `summit-insurance-subnet-zone2`
   - `us-south-3` → `summit-insurance-subnet-zone3`
6. Click **Create**.

<!-- SCREENSHOT: ROKS cluster creation page showing VPC, worker flavor, and three zones with subnets assigned -->

**Verify:** The cluster appears in the Clusters list with status **Deploying**. You will continue with Lab 3.5 while the cluster provisions.

> **Why bx2.4x16?** This flavor provides a balanced mix of CPU and memory suitable for running Node.js application pods alongside Kafka consumer workers that make API calls to the AI inference service.
>
> **Why one worker node per zone (3 total)?** This is the minimum configuration for multi-zone high availability. Additional nodes can be added as load increases.

---

### Step 3 – Enable Observability Integration

Once the cluster status changes to **Normal**, connect it to the monitoring and logging instances you created in Lab 3.3.

**Enable Monitoring:**

1. Open the `summit-insurance-cluster` in the IBM Cloud console.
2. In the left menu, click **Integrations**.
3. Under **Monitoring**, click **Connect** (or **Enable**).
4. Select `summit-insurance-monitoring` from the list and confirm.

<!-- SCREENSHOT: Cluster Integrations page showing Monitoring section with instance dropdown -->

**Enable Logging:**

1. Still on the **Integrations** page, locate the **Logging** section.
2. Click **Connect** (or **Enable**).
3. Select `summit-insurance-logging` from the list and confirm.

<!-- SCREENSHOT: Cluster Integrations page showing Logging section with instance dropdown -->

**Verify:** Both integrations show a connected status. Open the IBM Cloud Monitoring instance — cluster nodes should appear in the Kubernetes dashboards within a few minutes.

---

### Step 4 – Create Additional IAM Authorization Policies

Add the authorization policies that allow the ROKS cluster to access other services.

1. Go to **Manage → Access (IAM) → Authorizations**.
2. Click **Create** and add each of the following policies:

   | Source Service | Source Instance | Target Service | Target Instance | Role |
   |---------------|----------------|---------------|----------------|------|
   | Kubernetes Service | `summit-insurance-cluster` | Secrets Manager | `summit-insurance-secrets-manager` | SecretsReader |
   | Kubernetes Service | `summit-insurance-cluster` | Key Protect | `summit-insurance-key-protect` | Reader |
   | Kubernetes Service | `summit-insurance-cluster` | Container Registry | All instances | Reader |

<!-- SCREENSHOT: IAM Authorizations page showing ROKS → Secrets Manager policy creation -->

**Verify:** All three new policies appear in the Authorizations list.

## Lab 3.6 – Provision Red Hat AI Inference

### Objective

Provision a Red Hat AI Inference project with the two models used by the Summit Insurance underwriting workflow, and store the access credentials securely in Secrets Manager.

### The Application's AI Requirements

The underwriting workflow uses AI for two specific tasks:

1. **Driver's License Image Processing** — A vision model reads an uploaded photo of the applicant's driver's license and extracts structured information (name, date of birth, license number, state, and address).
2. **Underwriting Rules Evaluation** — A text model evaluates the applicant's data against the company's underwriting business rules and returns an approval or denial decision with written reasoning.

| Task | Model Used | Why |
|------|-----------|-----|
| License image scanning | `llama-3-2-11b-vision-instruct` | Vision-capable model; understands varied license layouts across all U.S. states |
| Underwriting evaluation | `granite-4-0-h-small` | IBM enterprise-optimized text model; fast and cost-effective for structured rule reasoning |

---

### Step 1 – Create Red Hat AI Inference Project

1. In the IBM Cloud console, click **Catalog**.
2. Search for `Red Hat AI Inference` and select it.
3. Configure the following:
   - **Region:** Select the region where Red Hat AI Inference is available (refer to current IBM Cloud documentation for supported regions)
   - **Project name:** `summit-insurance-underwriting`
   - **Description:** `AI inference for Summit Insurance underwriting workflow`
4. Click **Create**.

<!-- SCREENSHOT: Red Hat AI Inference project creation page -->

5. Once the project is created, navigate to the **Models** section and enable the following two models:
   - `llama-3-2-11b-vision-instruct`
   - `granite-4-0-h-small`

<!-- SCREENSHOT: RHAII Models page showing both models enabled -->

6. On the project overview page, locate and record the **Project ID**. You will need this when configuring the application in Section 4.

**Verify:** The project is active and both models show as enabled.

---

### Step 2 – Create a Service ID for Application Access

Applications must authenticate to Red Hat AI Inference using a Service ID — not a personal user API key. Service IDs are designed for applications: they can be scoped to specific resources, rotated independently, and audited in Activity Tracker.

1. In the IBM Cloud console, go to **Manage → Access (IAM) → Service IDs**.
2. Click **Create**.
3. Configure:
   - **Name:** `summit-insurance-rhaii-service-id`
   - **Description:** `Service ID for Summit Insurance application to access Red Hat AI Inference`
4. Click **Create**.

### Step 3 – Create a SecretStore

The SecretStore resource tells the External Secrets Operator where Secrets Manager is located and how to authenticate to it. You will create it using the YAML editor in the OpenShift console.

1. In the OpenShift console, make sure you are in the **summit-insurance** project.
2. Navigate to **Operators → Installed Operators → External Secrets Operator**.
3. Click the **SecretStore** tab and then **Create SecretStore**.
4. Switch to the YAML view and replace the contents with the following. Replace `<YOUR_SECRETS_MANAGER_URL>` with the endpoint URL from your Secrets Manager instance overview page, and replace `<YOUR_API_KEY>` with your Service ID API key from your TechZone reservation details:

```yaml
apiVersion: external-secrets.io/v1beta1
kind: SecretStore
metadata:
  name: ibm-secrets-manager
  namespace: summit-insurance
spec:
  provider:
    ibm:
      serviceUrl: <YOUR_SECRETS_MANAGER_URL>
      auth:
        secretRef:
          secretApiKey:
            name: sm-api-key
            key: apiKey
```

5. Before applying this, create the Kubernetes Secret that holds the authentication key. Navigate to **Workloads → Secrets** in the `summit-insurance` project.
6. Click **Create → Key/value secret**.
7. Configure:

   - **Key:** `apiKey`
   - **Value:** Your Service ID API key from the TechZone reservation

### Troubleshooting Common Issues

#### External Secrets Not Syncing

**Symptoms:** An ExternalSecret shows an error status. The corresponding Kubernetes Secret is not created or is not being updated.

**What to check:**
1. Navigate to the ExternalSecret resource in the OpenShift console and click on it to view the status and events. The event message usually identifies the cause.
2. Verify the IAM authorization policy exists for Kubernetes Service → Secrets Manager (SecretsReader).
3. Verify the secret name in the ExternalSecret YAML matches exactly the name stored in Secrets Manager (case-sensitive).
4. Verify the `sm-api-key` Kubernetes Secret contains the correct API key value.

#### Database Connection Issues

**Symptoms:** Application pods cannot reach the database. Connection attempts time out.

**What to check:**
1. Open the database instance in the IBM Cloud console and navigate to **Security → Allowlists**. Confirm the ROKS subnet CIDRs are listed.
2. Confirm the subnet CIDRs you entered match the actual subnets assigned to the cluster. You can verify these in **VPC Infrastructure → Subnets**.
3. Confirm the private endpoint is enabled on the database instance.

#### RHAII API Calls Failing (401 or 403 errors)

**What to check:**
1. Confirm the Service ID (`summit-insurance-rhaii-service-id`) has the Writer role assigned on the `summit-insurance-underwriting` project in Red Hat AI Inference.
2. Confirm the API key stored in Secrets Manager is the same key that was generated for the Service ID (not a different key).
3. Note that IAM access tokens expire after 1 hour. The application must implement token refresh logic.

#### Metrics or Logs Not Appearing in Dashboards

**What to check:**
1. In the OpenShift console, navigate to **Workloads → DaemonSets** in the `ibm-observe` namespace. Confirm the agent DaemonSets are running and show all pods as ready.
2. In the IBM Cloud console, open the cluster and go to **Integrations**. Confirm both Monitoring and Logging show as connected.
3. Wait a few minutes — it can take up to 5 minutes after enabling integrations for data to begin appearing in the dashboards.
